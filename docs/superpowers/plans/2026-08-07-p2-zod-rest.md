# P2 代码改进 批次2：zod 字段校验 + REST 统一

**日期**：2026-08-07
**范围**：延续批次1 的「范围外」项。用户已选 zod 做字段校验。本批实现 zod 写端点校验 + REST 统一（next(error) + ApiError + 状态码 + 路由命名审计）。

## 背景
- 字段校验散落各 handler 手写（`if(!recipeId)` / `if(!['mining',...].includes(skillType))` / `typeof battleId !== 'string'`），消息与行为不一，缺统一类型推断。
- 错误处理：全局中间件硬编码 500，`next(error)` 只能产 500，故各 handler 自行 `console.error + fail(500, '...')`，boilerplate 重复；ad-hoc `Error & {code}`（gathering `GATHERING_ALREADY_ACTIVE`、processing `INSUFFICIENT_MATERIALS`/`PLAYER_NOT_FOUND`）靠 handler 内 code 字符串匹配映射状态码，脆弱。
- 批次1 已统一响应信封（ok/fail + success:false），本批在此基础上把错误「流」也统一。

## 方案

### P2-3 zod 字段校验
- 装 `zod@^3.25`（v3 API 稳定：`errorMap` / `required_error` / `invalid_type_error` / `.trim()` / `.default()`）。
- 新增 `src/middleware/validate.ts`：`validate(schema, source='body')` -- `safeParse` 失败 `next(ApiError(400, 首条 issue 消息))`，通过则 `Object.assign(req, {[source]: result.data})` 替换为解析值（含 default/trim）。
- 新增 `src/validations/{auth,gathering,crafting,processing,characters,battle}.ts`：schema 自定义 message 逐一对齐既有测试断言（`Password must be at least 6 characters`、`recipeType is required`、`quantity must be a positive integer`、`Invalid skill type`、`battleId is required (string)` 等）。enum 用 `errorMap: () => ({ message })` 覆盖缺失+非法两态；必填字符串用 `required_error`+`invalid_type_error`+`min(1)` 三态同消息；quantity 用 `.int().positive().default(1)`。
- 写端点挂 `validate(schema)`（auth register/login、gathering /start、crafting card/gear/consumable、processing /process、characters POST / + PUT /:id/name + PUT /:id/deck、battle /result），删手写校验。顺序：rateLimit/auth -> validate -> handler。
- empirically 验证 zod v3.25 `z.string().trim().min(1)` 是 trim 先于 min（空格串被拒），故 username/name 在校验层即归一化。

### P2-4 REST 统一
- 新增 `src/utils/ApiError.ts`：`class ApiError extends Error { status; code?(内部判别,不进响应); extra?(展开进响应,如 {missing}) }` + `isApiError`。
- 抽 `src/middleware/errorHandler.ts`（原 index.ts 内联）：状态感知 -- `ApiError` 按 `status` 返回（+ `extra` 展开），`ZodError` 返回 400，其余 500（生产屏蔽）。index.ts 与 10 个集成测试 app 均挂载，保证错误信封一致。
- 路由/控制器 catch 统一 `next(error)`（去 `console.error+fail(500)` boilerplate，全局处理器统一 log+mask）。
- ad-hoc `Error & {code}` 收敛为 `ApiError`：gathering `GATHERING_ALREADY_ACTIVE` -> `ApiError(400, 'Already has active gathering task')`；processing 路由内 `INSUFFICIENT_MATERIALS` -> `ApiError(400, 'Insufficient materials', {extra:{missing}})`、`PLAYER_NOT_FOUND` -> `ApiError(404, 'Player not found')`。
- `result.success` 返回对象型服务（crafting/characters/battle/gathering-efficiency）保留显式 `fail()` 映射（改 throw 需重写所有 mock，风险高收益低）。
- matchmaking LOSER 兜底（409+`data.battleId` / 400 兜底 + WS emit）逻辑复杂，保留原 code-matching 结构不动。
- auth/rateLimit 中间件 401/429 补 `success:false` 保持信封一致。

### P2-5 路由命名审计
- 现状：资源型（`/api/characters`、`/api/cards`、`/api/match/queue`、`/api/warehouse`、`/api/skills`、`/api/professions`）+ action 型（`/api/gathering/start|complete|cancel`、`/api/battle/result`、`/api/processing/process`）混用。action 型有意为之（语义清晰），无 correctness 问题。HTTP 状态码现已一致（400/401/403/404/409/429/500/201）。**结论：无需改名**，记为未来可选 polish。
